## やり方（この 2 日で固まった形）

- **相談のセッション**（このセッション、Claude Code の Opus 5.5）が設計と取り込みと配信をする。作業は **1 つの作業 = 1 つの worktree（../care72-tNN）と branch（task/tNN）** で Opus（effort high）の作業者に出す。作業者は PR を integrate/t11-t12 宛に出し、merge はしない。相談のセッションが merge commit で取り込み、全部のテスト（vitest）と型の検査を通してから main と integrate に push し、本番に出す。
- **頼み文は Fable（xhigh）が書く**ことが多い。洗い出しの結果（作業者の監査）→ Fable が頼み文 → Opus に並列で 4 本前後、の形。頼み文には毎回「越えない線」（色と連絡順はルールの表だけ・AI は触れない・119 は出し分けない・仮名化の門・端末を増やさない・使わない語・避ける見た目の型）を入れる。
- **作業者の問いには相談のセッションが答える**。線に関わる物は「案」として DECISIONS に書き、作者に朝まとめて聞く。
- **点検は作業者とは別の目で**: 審査員の目の通し（手元の dev と headless Chrome）、安全とプライバシーの見直し、正しさの見直しを、それぞれ別の作業者に読むだけで頼み、見つかった物を次の作業に回した。
- **ほかのセッション**: 返信のセッション（アンケートの作り直し T65、紙の Word）、画面を見るセッション（手元の画面を見て指摘を記録、T66・T85 の頼み）、動画のセッション（提出動画の撮り直し）。それぞれ PR を出し、相談のセッションが取り込む。

## うまくいった事・失敗した事

- うまくいった: 洗い出し（読むだけの監査）→ Fable の頼み文 → Opus 4 体の並列 → 取り込みと配信、の回し方。問いに答えながら回すと、作業者が線を越えずに進む。別の目の点検（審査員の目・安全・正しさ）で、作った本人には見えない穴が毎回見つかった
- 失敗と直し:
  - python が空の案内で記録が書けていなかった → node で書く
  - 時刻を体感で書いて取り違えた → node で JST から作る
  - 返信のセッションが同じ docs の worktree を使い頼み文を上書き → docs の worktree は 1 つのセッションだけ
  - 配信の作り直しが外部キーで落ちる所を、リンクが作られる前に手元で再現して先に直せた
  - 作り直しの配信が途中で落ちて本番が空になった → 表を落とさない配信を既定に
  - マイクを本物で録った → 偽の機器を頼み文に
  - 鍵のファイルの中身を出す命令でパスワードが出た → 中身を出す命令を打たない・打たせない（記憶にも残した）
