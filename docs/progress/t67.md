## 値と理由

| 用途 | 前 | 後 | 理由 |
| --- | --- | --- | --- |
| form_read（Opus） | high・16000・180 秒 | 同じ | もとから high |
| scoring（Opus） | high・16000・180 秒 | 同じ | もとから high |
| director（Opus） | medium・16000・120 秒 | high・16000・180 秒 | Opus の high は様式の読み取り・講評と同じ 180 秒にそろえた。仮想モードの 1 回呼びもこれ |
| ledger_input（Sonnet。写真・PDF は Opus） | medium・16000・120 秒 | high・16000・180 秒 | lib/intake/read.ts は Opus で写真・PDF を読み、form_read と同じ形の重さになる |
| summary（Sonnet） | low・8000・90 秒 | high・16000・180 秒 | 考えた分も max_tokens に入る（超えると AiBadOutput の max_tokens で、再試行しない）。今は呼ぶ所が無い |
| persona（Haiku） | low・4000・60 秒 | high・8000・90 秒 | 下の「本人役」 |
| classify（Haiku） | low・4000・12 秒 | 同じ | 録音の応答のあと waitUntil の 30 秒に再試行込みで収める（12 秒 × 2） |
| 部屋の 1 刻み（ROOM_TIMEOUT_MS） | 60 秒 | 120 秒 | 下の「部屋」 |
| 部屋の Agent | medium・版 2 | high・版 3 | 版を上げないと本番の ai_agents の Agent（medium）が使われ続ける |

本人役: 訓練の 1 刻みは 監督（Opus 1 回）→ 本人役（Haiku × 10、Promise.all）の順に 1 要求の中で呼ぶ。Cloudflare の文書では Workers の 1 要求は外への接続（fetch）を同時に 6 本までしか開かず、7 本目からは前の接続が閉じるまで待つ。SDK の待ち（timeoutMs）は fetch を呼んだときから数えるので、後の 4 人は「前の呼び出しが終わるまで + 自分の呼び出し」で 1 回分の約 2 倍かかる。high で考える分が増えるので 60 → 90 秒にした。上限の 4000 は、考える分が入ると超えやすい（超えるとその人はその刻み「連絡なし」になり、静かに抜ける）ので 8000。16000 にしないのは、Haiku が 16000 を出しきるには 90 秒を超えるので、待ちと釣り合わないため。電話に出た人の言う事（personaCallReply、1 回だけ）も同じ設定になる。

部屋: Managed Agents の session の中で Opus が考えてから world_step を呼び、結果を返して idle になるまでを 1.5 秒ごとに読む。high で考える分が延び、60 秒だと時間切れ → 1 回呼び（もう 1 回の Opus、180 秒）に落ちる刻みが増える（費用が 2 倍、1 回呼びは前の刻みを覚えていない）。120 秒にした。時間切れのあとに届いた world_step は次の刻みで settlePending が片付ける（前のまま）。

1 刻みの要求が切れないか: ブラウザの fetch（components/drill/DrillControls.tsx の進める・早送り、ActionPanel の手）には待ちの上限が無い（AbortSignal なし）。Cloudflare の文書では Workers の HTTP の要求は接続が続く間は壁時計の上限が無く、CPU の上限は API の待ちを数えない。wrangler.jsonc に limits の設定も無い。なので、長くなっても切れるのはここに書いた待ちだけ。いちばん長い道（部屋 120 秒 → 1 回呼び 180 秒 × 2 → 本人役 90 秒 × 2）はどれも失敗の道で、そのときは本人役が「連絡なし」、世界が「代替」「停止」になって進む（止まらない）。

## Claude を使う所と使わない所

- 変えたのは考える深さだけ。使う所（監督・世界・本人役・台帳の入力・様式・講評）と使わない所（色と順位、誰が結末かの時計の計算）は変えていない
- 録音の分類は発災時の本人の録音で、応答のあとの短い時間に収める必要があるので low のまま
