## 選んだ道（1 の手から）

- **頁ごとに分けて並べて呼ぶ**（選んだ）: 切れた 10 件は 2 頁で 61〜82 欄、答えの JSON が 9,600 token ほど＋考える分 5,500〜7,600 token で 16,000 に達していた。1 頁は 30〜40 欄なので、答えは上限の半分ほどに収まる。待ちも 1 頁の分。読めた頁から見せられる
- **答えの形を短くする**（選んだ）: 評価の 1 回目の本物の答え（福山市 65 欄・時津町 71 欄・架空の 3 様式）をこの形に直すと、文字で 15〜22% 短い（欄 1 つ 125〜135 token → 100 token ほどの見積もり）。思ったほど縮まないのは、欄の名前・理由・場所の数が中身だから。頁を分けたので、これ以上縮める（キーを 1 字に・場所を千分率の整数に）のはやめた
- **出力の上限の見直し**（選んだ）: 16000 → 20000。待ち（180 秒）に収まる数（Opus の出力は 1 秒に 130 token ほど）
- **途中までの答えを捨てずに続きを頼む**（選んだ）: 前の答えに付け足す形（prefill）は Opus 5.5 で使えないので、読み済みの欄の名前を渡す新しい呼び出しにした。頁を分けたので、切れるのは欄の非常に多い 1 頁だけの見込み
- **流して受ける（streaming）**（選ばない）: SDK の待ちは流す形だと最初の応答までしか効かず、自前の待ちが要る。askJson・偽の client・評価の台の記録（fetch を包む）を全部替える手間に見合わない。1 頁の答えは上限より十分小さい
- **考える分（effort）**（変えない）: 考える分は出力の 3〜4 割。medium に下げれば速く安いが、欄の当たりと場所が落ちないかは本物でしか測れない。本物の 2 回目で high のまま測り、別の回で medium と比べるのがよい（問い 2）

## 1 様式の読み取りの見込み（本物の 2 回目で確かめる）

## 決めた所（docs/DECISIONS.md「書類」の案（T120））

- 様式の読み取りは 1 頁 1 回で並べる。読めなかった頁があっても読めた頁で保存し、再読で足す
- 続きは新しい呼び出しで 1 回だけ。streaming は使わない。effort は high のまま
- 区切りの空きは options と optionBoxes を使う（新しい欄を作らない。選ぶ欄の選択肢の □ と同じ持ち方で、画面の直し方も同じ）
- 同意の欄は項目なしのまま候補を出し、人が採用する
- 入れる欄の長い文は 3 塊（12,000 字）まで。どれかの塊が失敗すれば全体を失敗に（読めた塊だけで差分にしない）
- HEIC の部品は足さない（LGPL）
- 正解の表を直したのは 2 か所（移動手段を T112 の形に、同意の欄の項目なしを別解に）。台の数え方を直したのは空き枠（T111 の決めのとおり）。AI の側を直したのは欄の説明と決まり（移動手段・寝たきり・機器の中身・連絡先・薬の置き場）。手書きの外れ（findings の 9）の中身は読み違いでなく取り違え（機器の中身に種類の名前、連絡先の補足に名前・電話・夜間・種類の言葉、薬の置き場）だったので、画像の前処理は変えていない
