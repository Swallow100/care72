# T73 運用の守り（事業所と最初の管理者を作る道具、migration だけ当てる配信、作り直しの守り）（Opus、分岐）

このプロジェクトを知らないエージェントは、先に `docs/tasks/CONTEXT.md`（何を作っているか・越えない線・地図・進め方）→ `CLAUDE.md` → `docs/tasks/README.md` を読む。元は docs/progress/real-use-audit-20261104.md の 7 と「11/8 までに直すと効く順」の 11。この文書は、それ以外に何も知らなくても作業できるように書いてある。

## 意図（なぜこの作業か）

実際に使うときに使える形にする。本物の事業所が使い始めるとき、今の道具では 2 つで詰まる。

- 事業所と最初の管理者を作る画面・道具が無い（協力事業所のアカウントは seed/people.ts:69-75 で ID・パスワードが空。新規登録は作らない〔docs/DECISIONS.md「アカウントと事業所」〕ので、作るのは作者が端末で打つ道具）。
- 配信の作り直し（tools/deploy/rebuild-remote.sh）は、survey_ のほかの表を全部 DROP して migrations を 0001 から流し直し、種を入れ直す。本物の事業所が使い始めたあとに流すと、その事業所の利用者が全部消える。
- 済んでいる物: survey_shares・survey_links が offices を外部キーで指していて、共有リンクが 1 本でもあると作り直しの DROP が COMMIT で落ちる件は、**別の作業者が migration 0021 で外部キー無しの表に建て直す**（11/4 深夜）。T73 ではこの件に触らない。rebuild-remote.sh の survey_ を落とさない決まり（KEEP）はそのまま。

線: この作業は Claude を呼ばない。画面は作らない。本物の D1 に触る命令（wrangler の --remote・deploy）はエージェントが打たず、作者が端末で打つ道具を直すだけ（フック tools/hooks/rules.ts が止める）。平文のパスワードを表・ファイル・ログ・commit に残さない。

## 作る物

1. **migration だけ当てる配信（先に 1 commit で出す。これからの既定の配信）**: `tools/deploy/migrate-remote.sh <commit>`。rebuild-remote.sh と同じ worktree（DEPLOY_DIR）・checkout・`npm ci` → `npx wrangler d1 migrations apply care72 --remote`（d1_migrations に無い番号だけ当たる。表は落とさない）→ `npm run -s cf:build` → `npx wrangler deploy` → `node tools/deploy/check-remote.mjs`（CHECK_COMMIT を渡す。rebuild-remote.sh の終わりと同じ）。種は入れ直さない（デモ事業所は毎朝 4 時の戻しと /office の「最初に戻す」で種に戻る。配信直後にデモを種に戻す道は作らない。作者が /office で「最初に戻す」を押す）。手順の文は tools/deploy/rebuild-remote.sh の頭の注と同じ形で、`docs/tasks/T27.md` の配信の節に 1 段落足す（「11/4 から配信は migrate-remote.sh。rebuild は作り直しが要るときだけ」。T72 が wrangler.jsonc に cron を足すが、`wrangler deploy` が triggers を一緒に出すので手順は変わらない、の 1 行も）。**この道具が前提にすること**: migrations は番号を足すだけで、入った番号のファイルを書き換えない（0001 が T16・T23・T30 で書き換えられてきた〔列の注が残っている〕のは、作り直しの配信だったから）。これを縛るテストを 1 件: `docs/deploy/migrations.lock`（番号ごとのファイル名と SHA-256。`node tools/deploy/lock-migrations.ts` で作り直す）と `migrations/` の今の中身を比べ、lock にある番号のファイルが変わっていれば落ちる（新しい番号は lock に無くてよい。lock を作り直す時は commit のメッセージに理由）。lock は 0001〜0016 と、T68〜T72 が足す 0017〜0024 が入ったあとに作者がもう一度作る（progress に書く）。
2. **作り直しの守り**: rebuild-remote.sh の DROP の前に守りの問いを流す（`tools/deploy/guard-remote.mjs` に中身を置き、node で呼ぶ。wrangler の JSON の読み方は rebuild-remote.sh の中の node -e と同じ）: (a) `people` のうち office_id が office-demo でない行の数、(b) `accounts` のうち seed/people.ts の SEED_ACCOUNTS に無い行の数、(c) `offices` のうち SEED_OFFICES に無い行の数、(d) `drills` のうちデモ事業所でない行の数。どれかが 0 でなければ「本物データあり 停止」と数を出して止める（終了コード 1）。環境変数 `ALLOW_DATA_LOSS=1` を付けたときだけ、数を出したうえで続ける（作者が意図して消す形。既定は止める）。survey_ の表は落とさないので数えない（KEEP のまま。0021 のあとは offices を落としても survey_ の外部キーで落ちない）。判定は純粋な関数（行の数の表 → 止める/続ける）に分け、テストで見る。
3. **事業所と最初の管理者を作る道具**: `tools/office/new-office.ts`（node で読む .ts。tools/hash-password.ts と同じ書き方）。引数: `--name <事業所名> --city <市町村> --login-id <ID> --display-name <管理者の名前> [--id office-xxx] [--plan-form matsuyama|cao] [--out <ファイル>]`。中で lib/office/forms.ts の parseStaffInput と同じ決まり（名前 20 字・ID の形・予約された ID は断る〔lib/auth/demo.ts の isReservedLoginId〕）で確かめ、lib/office/staff.ts の generateInitialPassword で初期パスワードを作り、lib/auth/password.ts の hashPassword でハッシュにして、`INSERT INTO offices (id, name, kind, city, plan_form, created_at)`（kind は regular）と `INSERT INTO accounts (id, office_id, role, is_office_admin, display_name, login_id, password_hash, created_at)`（care_manager・管理者 1）の SQL を **ファイルに書く**（既定 `$HOME/care72-new-office-<時刻>.sql`。リポジトリの外）。平文のパスワードは **標準出力に 1 回だけ**出し（「初期パスワード（今回だけ表示）」）、SQL のファイルにもログにも書かない。plan_form の既定は 市が「松山市」なら matsuyama、ほかは cao（内閣府の様式例。T68 が lib/forms/plan-form.ts に `defaultPlanForm(city)` を足す予定なので、T68 が integrate に入っていればそれを呼び、無ければ同じ決まりを道具の中に書いて T68 のあとに差し替える）。作者はそのファイルを `npx wrangler d1 execute care72 --remote --file=<ファイル>` で入れる（道具は打たない。終わりに打つ命令を出すだけ）。そのあと管理者が /office で自分のパスワードを変えられる（T61）。事業所の id は `office-<英数字 8 桁>`（crypto.randomUUID の頭。重なりは入れるときに PRIMARY KEY が止める）。offices に T68 が足す中心の列（center_lat・center_lng）は入れない（NULL。管理者が /office で置く）。
4. **テスト**: 1 の lock（作る → 比べる → 1 文字変えると落ちる）、2 の判定（行の数の表を渡して止める/続ける、ALLOW_DATA_LOSS）、3 の道具（SQL の文の形、平文が SQL に無い、ハッシュが lib/auth/password.ts の verifyPassword で通る、予約 ID・短い名前・市なしを断る、plan_form の既定、node:sqlite に 0001〜0016 を当てて SQL を流すと offices と accounts に 1 行ずつ入り lib/auth/principal.ts の login で入れる）。`npm test`・`npm run typecheck`。シェルの道具（.sh）は中身を読んで手で確かめ、`bash -n` で構文だけ通す（Windows の Git Bash）。
5. **docs**: docs/progress/t73.md（Claude を使う所・使わない所を 1 行。この作業は Claude を呼ばない）。配信の手順（既定は migrate、作り直しは guard のあと）を docs/tasks/T27.md の配信の節に。仕様と違う決めは docs/DECISIONS.md に案として（先頭の節の上に「### 11/4 HH:MM 案（T73 の Opus）」。時刻は端末の `date` で確かめてから）。

## 終わりの形

- 作者が `bash tools/deploy/migrate-remote.sh <commit>` で、表を落とさずに新しい migration だけ当てて配信できる。`bash tools/deploy/rebuild-remote.sh <commit>` は本物のデータがあれば止まり、`ALLOW_DATA_LOSS=1` のときだけ続く
- `node tools/office/new-office.ts --name … --city … --login-id … --display-name …` で、事業所と最初の管理者の SQL のファイルと、初期パスワードの 1 回の表示が出る
- `npm test`・`npm run typecheck` が通る。PR を integrate/t11-t12 宛に
