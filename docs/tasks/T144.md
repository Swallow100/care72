# T144 見本のケアマネで変えた物を審査員のデモ事業所に効かせない・審査員のアカウントを 3 つに

このプロジェクトを知らないエージェントは、先に `docs/tasks/CONTEXT.md` → `CLAUDE.md` → `docs/tasks/README.md` を読む。docs/SPEC.md の「審査員用の公開デモ」、docs/DECISIONS.md の「アカウントと事業所」（デモ事業所・審査員・T61・T79・T95・T115）を読む。コードは lib/auth（demo.ts・credential.ts・principal.ts・wall.ts）、lib/seed（reset.ts・sandbox.ts・cron.ts・demo.ts）、seed/people.ts（SEED_ACCOUNTS）、lib/office/staff.ts。

## 意図（なぜこの作業か）

審査員はデモ事業所に入り、ケアマネの役では見本のケアマネ（山本）の担当一覧の 10 人を開く。山本はログインの ID を持ち、作者が本番を触って確かめるときに使っている。両方が同じ事業所の同じ 10 人を触るので、山本で台帳を直す・訓練を回す・経過を書くと、毎朝 4 時の戻しまで審査員にもそのまま見える。

山本で確かめた物が、審査員の見る中身を変えないようにする。審査員の入口と見え方は 1 つも変えないのが一番の条件。

あわせて、審査員のアカウントを 3 つにする。3 つは同じデモ事業所を共有し、ある審査員が直した物はほかの審査員にも見える。同時に触っても互いの訓練を止めない。

## 作る物

1. 山本の書き込みを審査員の事業所から分ける形。案と理由を DECISIONS に（ほかの案があれば比べて選ぶ）。案の例:
   - 山本のログインを、デモ事業所と同じ種を持つ別の事業所（確認用）に入れる。審査員の担当一覧の持ち主のアカウントはログインの ID を持たない形にし、ログインの山本は確認用の事業所の別のアカウントにする
   - 確認用の事業所の 10 人は id が重ならない形で同じ中身。T70 の配役（who）で想定の表の行が当たる。台帳の中身は seed/people.ts の 10 人から写す仕組みだけを足し、10 人の中身には触らない（同時に動く作業が中身を埋める）
   - 毎朝 4 時の戻しで両方が種に戻る。「最初に戻す」で種に戻る
2. 審査員のアカウントを 3 つ
   - 今の審査員の入口は残し、2 つ足す。パスワードは今の審査員のパスワード（env）を 3 つで共有し、新しい秘密は作らない
   - アカウントは別々にし、書き手が分かる名前（審査員 1 など）。ケアマネの役で開く担当一覧は 3 つとも同じ 10 人。役変更・本人スマホ・家族スマホの入口も 3 つで同じ
   - 進行中の訓練はアカウントごとに持てる（同時に別の訓練を進められる）
   - 変えられないアカウント（FIXED_ACCOUNT_IDS）に足す
3. 守る所: 審査員のログイン・役変更（ケアマネ・医療班・本人スマホ・家族スマホ）・見える 10 人・訓練の固定の筋と動画の筋・種の終わった訓練・試用事業所（T115）は今どおり。変えられないアカウントの決まりを保つ。山本のパスワードの読み方（CAREMANAGER_DEMO_PASSWORD_HASH・CAREMANAGER_DEMO_PASSWORD・種のハッシュ）は今どおり使える
4. テスト
   - 山本で台帳を直す・訓練を始める・経過を書く・同意を変えた後に、審査員で開くデモ事業所の中身が種のまま
   - 審査員の操作が山本の側に効かない
   - 戻しで両方が種に戻る
   - 審査員 1 の変更が審査員 2 に見える。審査員 1 と 2 が同時に別の訓練を進められる。山本の確認用の変更は審査員に見えない
   - 今の全部のテストが通る
5. 本番への入れ方（migration が要るなら 0035、種の SQL の差し替え）と、入れた後に本番で確かめる手順を進みに書く。本番のデータの入れ替えは相談のセッションがする。作業者は本番に触らない
